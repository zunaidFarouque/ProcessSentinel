# ProcessSentinel 2.0: Modular Rule Engine

The goal is to transition ProcessSentinel from a hardcoded, single-purpose script into a **Modular Rule-Based Monitoring Engine**. 

Instead of a fixed set of tracking parameters, the app will allow users to create an unlimited number of "Monitors" (Rules). Each Monitor will have its own target, interval, state-tracking logic, and custom notification messages mapped to specific conditions.

## 1. Routing & Notification Channels (Rule-First Setup)

To make ProcessSentinel truly enterprise-ready, we will adopt a **Rule-First setup with Topic Aliases**. 

*   **Global Default**: Users define a "Default Channel" for the whole app.
*   **Topic Manager (Aliases)**: Users can define multiple notification endpoints in the settings (e.g., "My Phone", "Lab Slack", "IT Warnings") mapped to different `ntfy.sh` URLs.
*   **Rule-Level Overrides**: When building a rule, the user can select "Send to: [Default] ▼" or override it by picking any defined alias from a dropdown.

## 2. Brainstormed Features & Scenarios

Here is a brainstormed list of Monitor Types tailored for heavy computational workflows (like GIS, photogrammetry, data science), along with real-world scenarios.

### A. Process & Window Monitors
*   **The "Headless Daemon" (Instance Counter)**
    *   Checks for the existence of `.exe` files in the background. Triggers based on instance counts `< X` or `> Y`.
*   **The "Stateful Step-Down" (High-Watermark Tracking)**
    *   Tracks the decline of instances without spamming. (e.g. 3->2, 2->1 notifications).
    *   *Manual Override*: You can **Reset the State** of this monitor from the UI if you manually intervene.

### B. Resource Usage Monitors (CPU/RAM)
*   **The "Silent Hang" (CPU Floor)**
    *   Monitors the CPU % of a specific process. Alerts if it falls *below* a threshold for a sustained period.
*   **The "Memory Leak" (RAM Ceiling)**
    *   Monitors RAM usage of a process. Alerts if it exceeds a threshold.

### C. Advanced File & Log Monitors
*   **The "I/O Heartbeat" (Multi-Path & Filtered Stall Detector)**
    *   Monitors *one or more* directories for file modifications, applying specific file extension filters (e.g., `*.shp`, `*.txt`).
*   **The "Cascading Warning" (Storage)**
    *   A single monitor pointing to a drive (e.g., `C:\`) with multiple condition tiers (30GB, 20GB, 10GB), each with a custom message.
*   **The "Log Scanner" (Regex/Keyword Match)**
    *   Tails a `.txt` or `.log` file generated by your batch process. Alerts if a specific keyword is appended.

### D. Cross-Domain Monitors (NEW)
To make ProcessSentinel a universal "Swiss Army Knife" for any tech domain:

*   **HTTP Endpoint Monitor (Web Dev / API Backend)**
    *   *Concept*: Pings a URL (e.g., `http://localhost:8080/health` or `https://myapi.com`) every X minutes.
    *   *Scenario*: You are hosting a local Flask/Node.js server for data processing. If it crashes and returns a 500 error, or stops responding entirely, you get an alert.
*   **Local Port Monitor (Database / Sysadmin)**
    *   *Concept*: Checks if a local network port is actively listening.
    *   *Scenario*: Your background PostgreSQL database (`port 5432`) or Redis cache (`port 6379`) crashes silently. The port drops, and Sentinel alerts you immediately.
*   **GPU VRAM & Temperature Monitor (Machine Learning / 3D Rendering)**
    *   *Concept*: Hooks into system GPU metrics (e.g., via NVIDIA API/nvidia-smi).
    *   *Scenario*: You are training an AI/LLM overnight or rendering a Blender animation. If VRAM usage drops to 0% (training crashed) or GPU temperature exceeds 85°C, Sentinel pings you to prevent hardware damage.
*   **Directory Size Monitor (Video Editing / Backups)**
    *   *Concept*: Monitors the total size of a specific folder rather than the whole drive.
    *   *Scenario*: Adobe Premiere Pro's scratch cache or a daily backup folder is ballooning out of control. Alert when that specific folder exceeds 100 GB.

## 3. Technical Architecture Redesign

### Object-Oriented Configuration Management (`config_manager.py`)
Configuration saving and loading will be strictly object-oriented using `to_dict()` and `from_dict()` methods on every component.

### The Engine (`monitor.py`)
*   **`MonitorEngine`**: Loops through active `BaseMonitor` objects. 
*   **`BaseMonitor`**: An abstract class defining `check()`, `to_dict()`, `from_dict()`, and `reset_state()`.

---

## 4. UI / UX Paradigm Shift

1.  **Main Dashboard**: A scrollable list/table showing active Monitors with `[Edit]`, `[Delete]`, and **`[↺ Reset State]`** buttons.
2.  **Notification Channels Tab**: A place to add/edit/delete aliases ("My Phone", "IT Slack").
3.  **Add Monitor Wizard (Modal Dialog)**: Dynamic interface based on the type of monitor selected.
